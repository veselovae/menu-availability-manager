# Menu Availability Manager

Демо-приложение для управления доступностью позиций меню ресторана: можно отфильтровать меню по цеху и статусу, временно остановить продажу позиции с указанием причины и вернуть её в продажу.

**[Открыть Menu Availability Manager →](https://menu-availability-manager.vercel.app/)**

Проект показывает, как организовать интерактивное приложение на Next.js с типизированной предметной моделью, серверными обработчиками, валидацией данных и согласованным клиентским состоянием.

## Возможности

- Просмотр позиций кухни, бара и кондитерской.
- Фильтрация по цеху и статусу; фильтры сохраняются в URL и восстанавливаются при перезагрузке страницы.
- Остановка позиции по одной из причин: закончились продукты, проблема с оборудованием, качество или изменение меню.
- Указание срока остановки — до конца смены или до выбранного времени в пределах следующих 24 часов.
- Возврат позиции в продажу с запретом для позиций с нулевым остатком.
- Оптимистичное обновление интерфейса, откат при ошибке и уведомления о результате операции.
- Отдельные состояния загрузки, ошибки и пустого списка.

## Стек

- Next.js App Router и Route Handlers
- React 19 и TypeScript
- Tailwind CSS 4
- TanStack Query для серверных данных и мутаций
- Zustand для состояния интерфейса
- React Hook Form и Zod для форм и валидации

## Запуск локально

Требуется Node.js, совместимый с используемой версией Next.js.

```bash
npm install
npm run dev
```

Откройте [http://localhost:3000](http://localhost:3000).

Полезные команды:

```bash
npm run lint   # проверка ESLint
npm run build  # production-сборка
npm run start  # запуск production-сборки
```

## Как устроен проект

```text
src/
├── app/                  # страницы, layout и API Route Handlers
├── features/stop-list/   # интерфейс и логика стоп-листа
│   ├── api/               # клиент запросов к API
│   ├── model/             # запросы, мутации, фильтры и UI-состояние
│   └── ui/                # компоненты экрана
├── mocks/                 # начальные демонстрационные данные
├── server/                # серверное in-memory хранилище
├── shared/                # общие UI-компоненты, утилиты и схемы
└── types/                 # доменные TypeScript-типы
```

Страница остаётся Server Component: она читает фильтры из URL и передаёт их интерактивному клиентскому экрану. TanStack Query отвечает за данные меню и их кэш, а Zustand — только за состояние интерфейса, например открытую панель и уведомления.

## API

| Метод  | Endpoint                                      | Назначение                                          |
| ------ | --------------------------------------------- | --------------------------------------------------- |
| `GET`  | `/api/menu-items?shop=kitchen&status=stopped` | Получить список позиций с необязательными фильтрами |
| `POST` | `/api/menu-items/:id/stop`                    | Остановить позицию или изменить причину и срок      |
| `POST` | `/api/menu-items/:id/resume`                  | Вернуть позицию в продажу                           |

Для остановки передаются `reason` и `until`. Значение `until: null` означает, что позиция остановлена до конца смены. Для конкретного времени сервер проверяет, что оно в будущем, не дальше чем через 24 часа и кратно 15 минутам.

## Демонстрационный режим и ограничения

Вместо внешнего backend и базы данных используется серверное in-memory хранилище, заполненное mock-данными. Список доступен через API, а операции изменения имитируют задержку и периодические ошибки — так можно увидеть состояния ожидания и проверить откат оптимистичного обновления.

Данные не сохраняются между перезапусками. На Vercel и других serverless-платформах память также не является общим постоянным хранилищем: разные экземпляры могут видеть разное состояние, а изменения не гарантированно переживают запуск функции. Поэтому приложение подходит как портфолио-демо, но для реального использования потребуется подключить постоянную базу данных и убрать искусственные ошибки.

## Ключевые решения

- Фильтры находятся в URL — ссылку можно сохранить или отправить, а навигация Back/Forward восстанавливает предыдущий выбор.
- Состояние сервера не смешивается с состоянием интерфейса: данные принадлежат TanStack Query, UI-состояние — Zustand.
- Правила валидации переиспользуются на клиенте и в API; форма дополняет серверную схему только полем режима выбора времени.
- Оптимистичные мутации сохраняют снимок кэша, восстанавливают его при ошибке и затем синхронизируют данные повторным запросом.
