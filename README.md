# Coperto Stop List

Тестовое задание на позицию Middle Frontend Developer.

## Stack

- Next.js App Router
- React
- TypeScript
- Tailwind CSS
- TanStack Query
- Zustand
- React Hook Form
- Zod

## Run locally

Для установки зависимостей:

```bash
npm install
```

Для запуска проекта в режиме разработки:

```bash
npm run dev
```

После запуска приложение доступно по адресу:

[http://localhost:3000](http://localhost:3000)

Проверка production-сборки:

```bash
npm run build
```

Проверка ESLint:

```bash
npm run lint
```

## Архитектура

Приложение разделено на несколько уровней ответственности.

### `app`

Содержит Next.js App Router, корневые компоненты приложения и Route Handlers.

`page.tsx` отвечает за чтение параметров фильтрации из URL и передачу их в клиентскую часть приложения.

`app/api` содержит серверные HTTP-endpoints для работы с позициями меню.

### `features/stop-list`

Содержит всю функциональность, относящуюся непосредственно к стоп-листу.

Внутри фича дополнительно разделена на:

- `ui` - React-компоненты;
- `model` - состояние, React Query hooks, фильтры и бизнес-логика;
- `api` - HTTP-клиент для взаимодействия с Route Handlers.

### `mocks`

Содержит начальный набор позиций меню. Эти данные используются как seed для серверного in-memory хранилища.

### `server`

Содержит серверное хранилище состояния меню. В рамках тестового задания используется in-memory реализация без базы данных.

### `shared`

Содержит переиспользуемые части приложения:

- UI-компоненты;
- вспомогательные функции;
- обработку API-ошибок;
- общую Zod-валидацию.

### `types`

Содержит доменные TypeScript-типы приложения.

## Server / Client boundary

Разделение Server Components и Client Components выполнено осознанно.

`src/app/page.tsx` остается Server Component и отвечает за работу с searchParams.

Интерактивная часть стоп-листа является клиентской, поскольку использует `TanStack Query`, `Zustand`, `React Hook Form`, `пользовательские события`, `optimistic updates`.

Серверные данные меню не хранятся в Zustand.

TanStack Query используется как источник server state, а Zustand - только для состояния интерфейса, например:

- открыта ли панель;
- какая позиция выбрана;
- отображается ли toast.

## Моковые данные

Начальные данные находятся в `src/mocks/menu-items.ts`.

В приложении используется набор из нескольких позиций разных цехов: кухня, бар, кондитерская.

Среди них есть как доступные позиции, так и позиции, уже находящиеся в стоп-листе.

Также присутствует позиция с остатком 0, чтобы можно было проверить ограничение на возврат позиции в продажу.

## Фильтрация

Доступны два фильтра: по цеху и по статусу.

Состояние фильтров хранится в URL. Например:

```
/?shop=bar&status=stopped
```

Это позволяет сохранить выбранные фильтры:

- после перезагрузки страницы;
- при использовании кнопок Back/Forward браузера;

Для изменения URL используется клиентская навигация Next.js.

## API

Backend реализован через Next.js Route Handlers.

Получение списка меню:

```
GET /api/menu-items
```

Поддерживаются параметры фильтрации:

```
shop
status
```

Например:

```
GET /api/menu-items?shop=bar&status=stopped
```

Ответ содержит массив позиций меню. Для запроса списка добавлена искусственная задержка, чтобы можно было увидеть состояние загрузки интерфейса.

## Постановка позиции в стоп-лист

```
POST /api/menu-items/:id/stop

Тело запроса:
{ "reason": "out_of_stock", "until": null }
```

`reason` может принимать одно из значений:

```
out_of_stock
equipment
quality
menu_change
```

`until`:

- `null` - позиция находится в стоп-листе до конца смены;
- Если выбрано конкретное время, передается ISO-строка:

  ```json
  {
    "reason": "equipment",
    "until": "2026-09-24T20:30:00.000Z"
  }
  ```

Тот же endpoint используется при редактировании причины или времени уже остановленной позиции.

## Возврат позиции в продажу

```
POST /api/menu-items/:id/resume
```

Отдельное тело запроса не требуется.

Если остаток позиции равен 0, сервер отклоняет попытку вернуть ее в продажу. Это ограничение дополнительно отражено в интерфейсе - соответствующая кнопка недоступна.

## Валидация

Общие правила валидации описаны в:

```
src/shared/validation/menu.ts
```

Базовая Zod-схема `stopItemSchema` проверяет `reason` и `until` в серверном Route Handler. Клиентская `stopItemFormSchema` расширяет ее полем `untilMode` и требует выбрать время в режиме "До конкретного времени". Общие правила не дублируются; `untilMode` на сервер не отправляется.

Для причины стопа проверяется, что значение входит в допустимый набор причин.

Для конкретного времени проверяется:

- время находится строго в будущем;
- время не дальше 24 часов от текущего момента;
- используется шаг 15 минут.

При ошибке формы сообщение отображается рядом с соответствующим полем.

## Выбор времени

Поскольку конкретное время может быть выбрано только в пределах ближайших 24 часов и с шагом 15 минут, в интерфейсе используется список допустимых значений вместо календаря. Пример:

```
Сегодня, 20:15
Сегодня, 20:30
Сегодня, 20:45
Сегодня, 21:00
...
Завтра, 08:15
```

Допустимые значения генерируются в:

```
src/features/stop-list/model/stop-time.ts
```

## Работа с серверными данными

Server state управляется через TanStack Query.

Ключи запросов вынесены в:

```
src/features/stop-list/model/queries.ts
```

Пример логической структуры ключа:

```
["menu-items", "list", filters]
```

Фильтры являются частью query key, поэтому разные комбинации фильтров имеют независимый кэш.

## Optimistic update

Постановка позиции в стоп-лист и возврат в продажу выполняются оптимистично. Пользователь видит изменение статуса сразу, не дожидаясь завершения HTTP-запроса.

Перед изменением кэша выполняется:

```jsx
queryClient.cancelQueries(...)
```

Это предотвращает ситуацию, когда уже выполняющийся запрос возвращает старые данные и перезаписывает оптимистично обновленное состояние.

До изменения сохраняется snapshot предыдущего кэша. Если mutation завершается ошибкой, предыдущие данные восстанавливаются. После завершения mutation query инвалидируется, чтобы получить актуальное серверное состояние.

## Имитация ошибок API

Mutation endpoints намеренно содержат искусственную задержку в `600ms` и примерно в `20%` случаев возвращают серверную ошибку. Это позволяет проверить поведение optimistic update при реальной ошибке.

## In-memory storage

В рамках задания настоящий backend и база данных не используются.

При старте приложения хранилище создается на основании mock-данных. Это означает, что при перезапуске локального сервера состояние вернется к исходному.

На serverless-хостинге состояние ограничено временем жизни экземпляра функции: при новом запуске оно создается из seed заново, а разные экземпляры не имеют общей памяти. Поэтому сохранение изменений между запросами и пользователями не гарантируется. Для этого тестового задания такое ограничение ожидаемо.

## Обработка ошибок

Предусмотренные ошибки API возвращаются в формате `{ error: { code, message, details? } }` с соответствующим HTTP-статусом:

| HTTP-статус | Код                              | Причина                                                                                  |
| ----------- | -------------------------------- | ---------------------------------------------------------------------------------------- |
| 400         | `INVALID_SHOP`, `INVALID_STATUS` | Недопустимые параметры фильтрации в GET-запросе                                          |
| 400         | `INVALID_JSON`                   | Некорректный JSON при постановке в стоп                                                  |
| 400         | `VALIDATION_ERROR`               | Причина или срок стопа не прошли серверную валидацию; `details` содержит ошибки по полям |
| 404         | `NOT_FOUND`                      | Позиция с указанным ID не найдена                                                        |
| 409         | `OUT_OF_STOCK`                   | Попытка вернуть в продажу позицию с остатком 0                                           |
| 500         | `MOCK_SERVER_ERROR`              | Искусственная ошибка сохранения                                                          |

HTTP-клиент проверяет `response.ok`. При неуспешном ответе `parseApiError` из `src/shared/lib/api-error.ts` извлекает `error.message` и создает `Error`. Если ответ не является JSON или не содержит ожидаемого сообщения, используется текст "Произошла неизвестная ошибка". Сетевые ошибки `fetch` также передаются в обработчики TanStack Query.

При ошибке загрузки списка выполняется одна автоматическая повторная попытка (`retry: 1`). Если запрос снова завершается ошибкой, показывается состояние "Не удалось загрузить меню" с кнопкой "Повторить", вызывающей `refetch`. Подробности ошибки загрузки в этом блоке не выводятся.

Мутации автоматически не повторяются (`retry: false`). Перед оптимистичным изменением сохраняется текущий список; при ошибке `onError` восстанавливает этот snapshot. После завершения операции `onSettled` инвалидирует запросы меню для синхронизации с сервером. Пользователь получает тост с текстом ошибки, который скрывается через 4 секунды. Ошибка сохранения сама по себе не закрывает панель: можно исправить данные и повторить отправку.

Клиентские ошибки Zod показываются под соответствующим полем с красной обводкой; невалидная форма не отправляется. Серверные `details` сейчас не привязываются к полям формы: при серверной валидации показывается общий текст ошибки в тосте. При остатке 0 возврат в продажу дополнительно заблокирован в интерфейсе с подсказкой.

## Состояния интерфейса

Для списка предусмотрены отдельные состояния:

- `Loading` - отображается во время первоначальной загрузки данных;
- `Error` - показывается сообщение об ошибке и возможность повторить запрос;
- `Empty` - отображается, если по выбранным фильтрам нет подходящих позиций.
